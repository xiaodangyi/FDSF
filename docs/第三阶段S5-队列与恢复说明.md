# S5 消息队列与独立 worker

更新：2026-10-26。本阶段在本机 Ubuntu 完成，不需要购买服务器。

## 这一步解决什么

以前，网页进程直接做识别。现在分为三个程序：

1. Web：检查登录和图片，把原图和任务号保存到 SQLite，然后投递任务号。上传成功返回 HTTP 202。
2. Redis：保存排队消息，只传任务号，不传原图、密码或完整模型结果。
3. Celery worker：独立进程取号，从同一 SQLite/受控目录读取原图，运行识别，把结果写回。

可以把它理解成“前台取号 → 排队 → 后台办理 → 按号查结果”。关闭网页不等于取消任务。重新登录后，可在历史记录中查询。

生产队列默认 `DESKVISION_QUEUE_MODE=celery`。`inline` 只用于明确选择的旧版本机调试/离线回归，它不是 S5 的交付队列。模式拼写错误、缺少 Redis URL 会拒绝启动，不静默切回网页执行。

## 文件与状态

| 文件 | 职责 |
|---|---|
| `deskvision/queueing.py` | 配置检查与投递，只发布任务号 |
| `deskvision/worker.py` | Linux prefork worker，任务并发 1、预取 1 |
| `deskvision/executor.py` | 原子领取、心跳、逐路保存与最终状态 |
| `deskvision/repository.py` | SQLite 原子更新、执行令牌和过期恢复 |
| `deskvision/task_service.py` | 工作台保存原图、建任务、投递 |
| `deskvision/web/app.py` | 快速提交任务，每 2 秒重新校验登录并查询当前账号的任务 |
| `environment/start_stage3_s5.py` | Redis、worker、Web 启动入口 |
| `environment/manage_queue.py` | 管理员标记过期任务、补投尚未开始的任务 |

数据库自动升级至 schema v3，增加 `execution_id`、`heartbeat_at`、`started_routes`；保留原有账号、历史和所有者。默认仍是 `runs/stage3.sqlite3`；独立测试通过 `DESKVISION_DATABASE` 使用临时数据库。Web 与 worker 必须使用同一份数据库、目录和代码版本，不能分别保存到两个系统的不同路径。

主状态：`queued → running → succeeded / partial_failed / failed`。`route_states` 单独展示所选路线的 `queued / running / ok / failed`，`results` 保存已完成路线的报告。两路分别读取原图，不把本地检测结果交给 DeepSeek。某一路先完成立即写入数据库，另一条失败不抹掉它。

## 在当前电脑启动

正式 worker 用 Ubuntu 的 Linux prefork，保持现有 GPU 版 PyTorch；本轮没有更换 torch 或安装 CPU 版。每个服务放一个 Ubuntu 终端，先在每个终端运行：

```bash
cd "/mnt/e/新建文件夹 (9)/FDSF"
source "$HOME/.venvs/deskvision-s1/bin/activate"
```

第一次安装队列依赖：

```bash
python -m pip install -r environment/requirements-s5.txt
```

如果是新 Ubuntu，还需按 `environment/README.md` 安装项目依赖，并通过系统包管理器安装 `redis-server`。当前电脑已经安装 Redis 8.0.5、Celery 5.6.2、redis-py 6.4.0。不要把 Python 客户端版本与 Redis 服务版本混为一谈。

三个终端分别执行：

```bash
# 终端 1：Redis。数据保存在忽略目录 .local/redis，端口 6380，只监听本机。
python environment/start_stage3_s5.py redis

# 终端 2：后台 worker，保持窗口打开。
python environment/start_stage3_s5.py worker

# 终端 3：工作台，保持窗口打开。
python environment/start_stage3_s5.py web --port 8001
```

浏览器登录地址：`http://127.0.0.1:8001/login`；工作台：`http://127.0.0.1:8001/ui/`。三个程序都在自己的电脑上，无需云服务器、域名或公网 Redis。

原有本机账号和 `.local/auth.json` 沿用，不重新生成密码。新机器先用 `python environment/manage_users.py init-local` 初始化私有密钥，再创建账号。权重、原图、SAM、DeepSeek 配置仍按原项目要求另备；只安装队列依赖不能替代模型配置。启动不会自动调用 DeepSeek，选择云端路线仍须明确同意发送原图和产生用量。

如果配置了自定义环境变量，三个终端要一致：

| 配置 | 当前启动器默认值 |
|---|---|
| `DESKVISION_QUEUE_MODE` | `celery` |
| `DESKVISION_REDIS_URL` | `redis://127.0.0.1:6380/0` |
| `DESKVISION_QUEUE_NAME` | `deskvision` |
| `DESKVISION_DATABASE` | 不设则使用项目 `runs/stage3.sqlite3` |

不要让 Windows Web 和 Ubuntu worker 使用不同数据库或互相无法解析的路径。S5 正式启动统一在 Ubuntu；Windows 仅保留显式 inline 回归。`GET /health` 只说明 Web 存活，不代表 Redis、worker 或模型已就绪。

## 停止与恢复

正常停止顺序：先停止接新任务的 Web，然后对 worker 按 `Ctrl+C`，等待正在执行的任务结束，最后停止 Redis。不要把强制关闭 Ubuntu 当作正常停止。Redis 开启 AOF，启动器设置 `appendfsync=everysec`；突然断电存在约最后一秒消息尚未落盘的窗口。验收隔离 Redis 使用 `always` 来确认实际重启恢复，不能把它当成突然断电零丢失证明。

| 情况 | 当前行为 |
|---|---|
| 浏览器关闭 / Web 重启 | queued 和心跳正常的 running 保留，独立 worker 继续执行 |
| 重复投递相同任务号 | SQLite 原子 `queued → running` 只成功一次，其他消息不再调用模型 |
| 投递未确认 / Redis 不可用 | 保存任务和原图，API 返回 503 加任务号；记录 `delivery_uncertain`，页面提示不要重复提交 |
| worker 未启动 | 任务保持 queued；启动同配置 worker 后继续取消息 |
| 某一路正常失败 | 保存路线错误；另一路成功则 partial_failed |
| DeepSeek 请求超时 / 连接中断 | 路线标记 `remote_result_unknown`，保留原始错误分类；用量待确认，不自动重试 |
| worker 崩溃 / 硬超时 | 每 5 秒心跳；超过 120 秒后，查询/历史页或恢复命令将任务标为失败或部分失败，保留成功路线 |
| DeepSeek 已开始但尚未保存结果时中断 | 标记结果/用量待确认，绝不自动再调用；管理员自行核对服务商用量 |
| 过期 worker 迟到写入 | 必须匹配当前运行状态和执行令牌，不能覆盖已恢复的终态 |

“已开始”采用保守定义：worker 进入 DeepSeek 路线前先写标记，可能早于实际网络请求，所以待确认不等于已经计费。无法通过本地队列保证外部服务恰好计费一次；当前策略是不自动重复调用。

默认软超时 1500 秒、硬超时 1800 秒；Redis 消息可见性超时 3600 秒。两路同时执行时，Python 线程中的阻塞调用未必能被软超时立即终止，硬超时负责最后终止子进程。下一次查询或管理员恢复时，再根据心跳标记中断。恢复为惰性检查，当前没有额外常驻定时清理进程。

同一 Ubuntu 项目环境中的管理员命令：

```bash
export DESKVISION_QUEUE_MODE=celery
export DESKVISION_REDIS_URL=redis://127.0.0.1:6380/0
python environment/manage_queue.py recover-expired
python environment/manage_queue.py redeliver <原任务号>
```

`redeliver` 只允许补投尚未执行的 queued 任务，复用原任务号。对于已经 running 或结束的任务拒绝补投。没有自动重跑、自动创建新任务、自动付费重试，也没有网页管理员补投按钮。

## 实际验收与复现

1. `python environment/verify_stage3_s5.py`：Windows / Linux 完整离线回归，模型被替换，不发外部请求。
2. Ubuntu 执行 `python environment/verify_stage3_s5_processes.py`：自动启动隔离 Redis、独立 HTTP 服务和真实 prefork worker；结束清理本次进程。
3. 完整浏览器验收：Ubuntu 执行 `python environment/verify_stage3_s5_processes.py --browser`，等待打印 `BROWSER_READY`，再在已安装 Playwright 和 Edge 的 Windows Node 环境执行 `node environment/verify_stage3_s5_browser.cjs`。脚本通过忽略目录传递随机临时账号，报告不记录密码。

过程验收不使用业务演示账号或正式数据库。模型函数使用 `environment/s5_offline_worker.py` 的离线替身，仅验证队列和页面行为，不能据白色测试图上的模拟“1 件”判断识别准确率。该替身入口只供测试，正式启动器不会使用它。

| 验收 | 结果与证据 |
|---|---|
| Windows 完整回归 | 116 项运行、115 项通过、1 项 Windows symlink 权限跳过；`reports/stage3-S5-windows-checks.*` |
| Ubuntu 完整回归 | 116 项全部通过；`reports/stage3-S5-linux-checks.*` |
| 实际 Redis / 独立进程 | 9 组检查通过；`reports/stage3-S5-process-checks.json` |
| 实际浏览器控件 | 文件选择、可见预览、入队提示、Timer 结果图、ZIP、跨账号拒绝、历史、退出通过；`reports/stage3-S5-browser-checks.json` |
| 强制中断 / 超时 | 真实 SIGKILL；真实 4 秒软 / 6 秒硬限制。随后注入过期心跳加快检查，不声称实际等待 120 秒 |
| DeepSeek 真实调用 | 0 次；本阶段未做真实双路推理或新增精度验收 |

进程证据保留 Web PID、worker 父/子 PID、两任务执行起止时间；可确认执行者不是 Web，也不是测试主进程。私有原始日志和截图留在 `.local/s5-processes/`、`runs/stage3/S5/`；只有脱敏摘要入 Git。

已知提示：Gradio 偶尔在上传完成后请求 `upload_progress?upload_id=undefined` 返回 404，实际上传、预览、按钮和识别结果链路均通过；浏览器报告作为 warning 保留。Windows 回归仍有 Gradio/asyncio ResourceWarning 与框架弃用提示，未当作已修复。

## 对 S4 记录的纠正

S4 历史浏览器脚本用浏览器上下文的 HTTP 客户端调用 upload/set_image，证明了接口回调和文件隔离，但不足以证明实际文件控件更新预览。S5 发现并修复 FileData 中同源绝对 URL 的误拦截与上传进度的会话绑定；新 S5 脚本直接操作真实 file input、点击识别按钮并等待可见结果。S4 原报告按历史保留，实际控件链路以 S5 新报告为准。
